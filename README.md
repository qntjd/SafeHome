## 📌 프로젝트 소개

SafeHome은 경찰청·행정안전부 등 공공데이터를 기반으로 1인 가구, 특히 여성·청년의 안전한 생활을 지원하는 플랫폼입니다.
혼자 사는 사람들이 귀갓길부터 집 안까지 안심할 수 있도록 안전 지도, 안심 귀가, 긴급 SOS, 실시간 재난 알림, AI 안전 브리핑 기능을 웹과 안드로이드 앱으로 제공하며, AWS 클라우드 환경에 실제로 배포·운영하고 있습니다.

웹(React)·안드로이드(Kotlin) 두 클라이언트가 단일 Spring Boot API 서버를 공유하며, 기획부터 백엔드·프론트·안드로이드·인프라·배포까지 **1인이 개발·운영**하고 있습니다.

## 🚀 주요 기능

### 🗺 안전 지도
- 전국 CCTV(377,000+건) · 비상벨(88,000+건) · 경찰서·파출소(2,000+건) 마커 표시, 대구 단일 지역 → **전국 17개 시/도**로 커버리지 확장
- 시설 종류별 필터링(토글 버튼), 현재 위치 기반 반경 검색
- 반경 검색 쿼리 **인덱스 + Bounding Box** 최적화 (5,101ms → 8.8ms, 약 580배 단축)
- 밀집 지역 마커 과다 렌더링 방지를 위한 **거리순 정렬 + 상위 300건 제한**, 통계 카운트는 별도 API로 분리해 정확도 유지
- 마커 아이콘 **비트맵 캐싱**으로 렌더링 부하 개선 (O(N) → O(1))

### 📊 동네 안전점수
- CCTV 밀도(30%) + 범죄 역점수(40%) + 비상벨 밀도(10%) + 가로등(20%) 가중 합산, A~F 등급 자동 부여
- Spring Scheduler로 매일 새벽 4시 자동 재계산, Redis 캐싱으로 응답 성능 최적화

### 🚶 안심 귀가
- 즐겨찾기 장소 저장, 안전 경로 분석(CCTV·비상벨·경찰서 밀도 기반 안전점수)
- 귀가 중 주변 위험 알림, 위치 공유 링크(비로그인 확인 가능)
- 야간 모드(오후 10시~오전 6시 자동 전환), 워치독 패턴(예상 도착 시각 초과 시 자동 알림)

### 🚨 긴급 SOS (웹 + 안드로이드)
**웹**
- 수동 SOS, 음성 자동 감지(Web Speech API), 5초 카운트다운 후 비상연락처 알림, 112 연결

**안드로이드**
- **백그라운드 음성 SOS** — Foreground Service로 화면이 꺼진 상태에서도 상시 음성 감지, 잠금화면 위 SOS 화면 자동 표시
- **잠금화면 SOS + 카운트다운** — 카운트다운 중 취소 가능(오작동 방지), 종료 시 비상연락처 SMS 자동 발송
- **SOS 자동 녹음·녹화** — 음성 녹음 및 Camera2 기반 백그라운드 영상 녹화(화면 프리뷰 없이, 최대 2분, 별도 Foreground Service로 액티비티 종료와 무관하게 지속)
- **112 자동신고 (고급 기능)** — 설정에서 토글, 카운트다운 종료 시 `ACTION_CALL`로 자동 발신(권한 미허용 시 다이얼 화면 대체)
- **SAFE HOME 사용 가이드** — 앱 핵심 기능 안내 + SOS 설정 강조
- **생활 안전 정보** — 휴대폰 자체 긴급 SOS(갤럭시·아이폰) 설정 안내 + 명의도용방지·개인정보 포털 등 공공 안전 서비스 연계

### 🔔 실시간 알림
- SSE 기반 실시간 재난문자 수신, 시도/시군구 단위 알림 구독
- **내 지역**(GPS 자동 감지·구독) / **관심 지역**(부모님댁 등 수동 등록) 탭 분리
- 행정안전부 재난문자 API 주기적 수집

### 📈 범죄통계 시각화
- **2020~2024년 5개년** 전국 17개 시/도 범죄 통계 (강력·폭행·절도·사기지능·풍속마약·**교통**·기타 7개 분류로 세분화)
- 지역별·연도별 조회 API 및 연도별 추이(trend) API 제공
- 웹: 스택 바 차트·레이더 차트 / 안드로이드: 연도 탭 전환 막대그래프

### 📰 안전 뉴스
- 전국 단위 안전·재난·범죄 키워드 뉴스 수집, 신뢰 언론사 필터링

### 🤖 AI 안전 브리핑

- 지연시간·비용이 낮은 Haiku 모델로 실시간 생성에 적합한 응답 속도 확보

### 왜 이 기술을 선택했는가

- **PostgreSQL**: 위치 기반 반경 검색이 핵심 기능이라 위경도 컬럼에 대한 인덱스·범위 쿼리 최적화가 중요했고, JSON 타입과 지리 데이터 확장 가능성을 함께 고려해 선택. 이후 Bounding Box 사전 필터링 최적화의 기반이 됨.
- **Redis (Cache-Aside)**: 안전지도 조회처럼 읽기 비중이 압도적으로 높은 API의 응답 속도를 낮추기 위해 도입. `@Cacheable` 대신 `RedisTemplate` + `ObjectMapper`로 직접 캐시 로직을 짜서 캐시 무효화 시점과 직렬화 방식을 명시적으로 제어.
- **SSE (WebSocket 대신)**: 재난 알림은 서버 → 클라이언트 단방향 푸시만 필요해, 양방향 연결·핸드셰이크 오버헤드가 있는 WebSocket보다 가볍고 HTTP 인프라(Nginx, 방화벽)와 궁합이 좋은 SSE를 선택.
- **Kotlin Coroutines**: Android에서 위치 추적·음성 감지처럼 오래 실행되는 비동기 작업이 많아, 콜백 지옥을 피하고 생명주기에 안전하게 묶기 위해 콜백 기반 API 대신 채택.
- **Docker Compose (단일 EC2 인스턴스)**: 예산 제약(AWS 프리티어) 안에서 PostgreSQL·Redis·배치를 격리된 환경으로 재현 가능하게 운영하기 위한 실용적 선택. 쿠버네티스 같은 오케스트레이션은 현재 트래픽 규모에 과했다고 판단.
- **Claude Haiku (AI 브리핑)**: 사용자 위치 기반 요약을 실시간으로 생성해야 해서 응답 속도와 비용이 중요했고, 더 큰 모델 대비 지연시간·비용이 낮은 Haiku로 충분한 품질이 나와 선택.

## 🔥 트러블슈팅 상세

실제 운영 환경(AWS EC2)에서 발생한 장애를 직접 진단하고 해결한 기록입니다. 각 항목은 **문제 → 원인 → 해결 → 배운 점** 순으로 정리했습니다.

### 1. 시스템 메모리 고갈로 인한 로그인 장애

- **문제**: 운영 서버에서 간헐적으로 `CannotCreateTransactionException` 발생, 사용자 로그인 실패
- **원인 추적**: 처음엔 DB 커넥션 풀 고갈을 의심 → `pg_stat_activity`로 확인한 결과 커넥션은 11개만 사용 중으로 정상. 애플리케이션 레이어가 아니라 인프라 레이어를 의심해 `free -h`로 확인하니 여유 메모리가 66MB, 스왑은 0으로 시스템 자체가 메모리 부족 상태였음
- **해결**: JVM이 새 `EntityManager`/`Connection` 객체를 할당하지 못해 발생한 문제로 확인, 스왑 메모리 추가 및 JVM 힙 제한(`-Xmx768m -Xms256m`) 설정을 개선 방향으로 확정
- **배운 점**: 같은 예외 메시지라도 원인은 매번 다를 수 있다. "이전에 이 에러는 이래서 났었다"는 가정으로 바로 뛰어들지 않고, 애플리케이션 → DB → 시스템 리소스 순으로 레이어별로 직접 검증하는 습관을 갖게 됨

### 2. HikariCP 커넥션 풀 고갈

- **문제**: 서버가 36일간 정상 운영되다가 갑자기 커넥션 풀이 고갈되며 API가 응답하지 않는 현상 발생
- **원인**: 기본 `RestTemplate` Bean에 `connectTimeout`/`readTimeout`이 설정되어 있지 않아, 재난 알림 배치가 외부 API를 3분 주기로 폴링하는 과정에서 응답이 느려질 때마다 스레드와 커넥션이 반환되지 않고 누적됨
- **해결**: `SimpleClientHttpRequestFactory`로 명시적 타임아웃(연결 5초, 읽기 10초)을 설정하고, 폴링 주기를 3분 → 5분으로 조정
- **배운 점**: 기본값(default)을 그대로 쓰는 설정이 당장은 문제없어 보여도, 장시간 운영(long-running) 환경에서는 예상치 못한 시점에 누적된 문제로 터질 수 있다는 것을 체감. 이후로는 외부 호출이 있는 클라이언트는 타임아웃을 항상 명시하는 습관을 들임

### 3. 배치 데이터 정합성 버그 (917만 건 중복)

- **문제**: CCTV·비상벨 데이터 배치를 실행할 때마다 DB 행 수가 비정상적으로 증가, 실제로는 3~4만 건이어야 할 데이터가 917만 건까지 쌓임
- **원인**: insert 시마다 새 UUID를 생성해서 넣고 있어 `ON CONFLICT` 충돌 감지가 무력화됨. 또한 페이지네이션 파라미터(`numOfRows=1000`)를 지정해도 공공 API가 페이지당 100건만 반환하는 걸 놓쳐 실제로는 데이터의 90%가 누락되고 있었음
- **해결**: 고유 식별자를 UUID 생성 대신 실제 데이터의 자연 키(`type`, `lat`, `lng`) 기준 UNIQUE 제약으로 변경해 `ON CONFLICT`가 정상 동작하도록 수정, 페이지네이션 루프를 API의 실제 반환 건수 기준으로 재작성
- **배운 점**: "몇 건이 들어왔는지"만 보고 배치가 정상 동작한다고 판단하면 안 되고, 기대값과 실제값을 반드시 대조해야 한다는 것을 배움. 외부 API 문서의 파라미터 스펙을 곧이곧대로 믿지 않고 실제 응답을 직접 확인하는 습관이 생김

### 4. CORS 설정 누락

- **문제**: 프로덕션 배포 후 이메일 인증 등 일부 API 호출이 403으로 실패
- **원인**: `SecurityConfig`의 `allowedOriginPatterns`에 로컬 개발 도메인만 등록되어 있고 실제 프로덕션 도메인(`https://safehome-api.duckdns.org`)이 빠져 있었음
- **해결**: 프로덕션 도메인을 `allowedOriginPatterns`에 추가
- **배운 점**: 로컬에서는 항상 통과되는 설정이라 배포 후에야 발견되는 문제였음. 이후 배포 체크리스트에 "프로덕션 도메인 CORS 등록 확인"을 명시적으로 추가

### 5. 예외가 조용히 삼켜지던 문제

- **문제**: 특정 요청이 500 에러로 실패하는데 서버 로그에 아무 흔적도 남지 않아 원인 파악이 불가능했음
- **원인**: `GlobalExceptionHandler`의 catch-all 블록이 예외를 잡아 응답만 내려줄 뿐 로깅을 하지 않고 있었음
- **해결**: `@Slf4j`와 `log.error("서버 오류 발생", e)`를 추가해 모든 미처리 예외가 스택트레이스와 함께 기록되도록 수정
- **배운 점**: 예외 처리와 예외 로깅은 다른 문제다. "에러가 나면 사용자에게 안내 메시지를 보여준다"는 요구사항만 채우고 로깅을 빠뜨리면, 운영 중 발생하는 실제 장애를 디버깅할 방법이 사라진다는 것을 절실히 느낌

## 💡 개발하며 배운 점

- **같은 에러 메시지 ≠ 같은 원인**: 과거에 특정 예외가 특정 원인으로 발생했더라도, 다음에 같은 예외가 나면 원인이 다를 수 있다. 매번 애플리케이션 → DB → 인프라 순으로 레이어를 나눠 직접 검증하는 습관이 생김
- **기본값을 믿지 않기**: 프레임워크의 기본 설정(타임아웃 없는 `RestTemplate` 등)은 초기에는 문제가 없어 보여도 장시간 운영 환경에서는 리스크가 된다는 것을 실제 장애로 체감
- **배치는 결과를 반드시 검증**: 배치가 "에러 없이 끝났다"는 것과 "정확하게 동작했다"는 것은 다르다. 기대값과 실제 데이터를 비교하는 검증 단계를 항상 포함시켜야 한다는 것을 배움
- **패키지명처럼 사소해 보이는 결정도 신중하게**: Play Store 등록 과정에서 패키지명 충돌로 Firebase, OAuth SHA-1 재등록을 포함한 전체 리팩터링을 겪으며, 초기 설계 단계의 사소한 결정이 나중에 큰 비용으로 돌아올 수 있음을 배움
- **인프라 예산 안에서 실용적으로 설계하기**: AWS 프리티어 t3.small(1.9GB RAM)이라는 제약 안에서 서비스를 운영하며, 스왑 메모리 부재처럼 예산 제약이 만들어내는 운영 리스크를 직접 경험하고 이를 고려한 설계(캐싱, 타임아웃, 폴링 주기 조정)의 중요성을 체감
